# 编码规范

## 1. 文档职责

本文定义实现代码时应主动遵守的共同规则；[Code Review 规范](CodeReview规范.md)负责交付前检查和评分。具体领域边界以 Architecture、ADR 和当前 Sprint 为准。

## 2. Python 与工具链

- 使用项目 `pyproject.toml` 声明的 Python 版本和依赖。
- 使用 `uv` 管理依赖和 Lock File，不手工维护 `requirements.txt` 或直接执行 `pip install`。
- 使用 Ruff 进行 Lint、Import 排序和格式检查，不手工制造另一套风格规则。
- 应用模块使用绝对导入，例如 `from app.services.auth_service import AuthService`。

## 3. 命名与类型

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| Python 文件 | `snake_case` | `chat_service.py` |
| 函数和变量 | `snake_case` | `create_session()` |
| 类和 Protocol | `PascalCase` | `StorageProvider` |
| 常量 | `UPPER_SNAKE_CASE` | `MAX_UPLOAD_SIZE_BYTES` |
| API Path | 小写、复数资源 | `/users/sessions` |
| 数据库对象 | `snake_case` | `refresh_token_hash` |

- Service、Repository、Provider 和公共 Utility 的方法必须有参数和返回类型。
- 使用明确 DTO、Schema、Dataclass 或 Protocol 表达跨层契约，避免无边界 `dict[str, object]`。
- `Any` 只能用于真实动态边界，并应在进入业务层前转换为稳定类型。

## 4. 分层与单一职责

```text
Router -> Service -> Repository / Provider
```

- Router 处理 HTTP，不写业务规则、SQL 或 Provider SDK 调用。
- Service 处理权限、事务、流程、补偿和业务日志，不直接写 SQL。
- Repository 处理数据访问，不决定 HTTP 或业务权限。
- Provider 隔离外部系统和 SDK，不知道当前用户或业务数据库。
- Model 描述数据库结构；Schema 描述输入输出；二者都不承担业务流程。

当函数同时处理协议、权限、数据库、外部 SDK 和响应组装时，应先按职责拆分，而不是继续增加条件分支。

## 5. 函数与控制流

- 一个函数完成一个可以清晰命名和测试的职责。
- 优先使用早返回减少深层嵌套，但不能隐藏重要状态转换。
- 业务分支使用 Enum、Literal 或有意义常量，不散落魔法字符串和数字。
- 不使用裸 `except`；只捕获当前层能够明确转换、补偿或记录的异常。
- 不用宽泛 `except Exception` 把编程错误伪装成业务失败；系统边界确需兜底时必须记录安全错误并保留测试。

## 6. Sync、Async 与 Streaming

- 只有调用链包含异步 I/O 或 Streaming 时才使用 `async`，不为了形式统一机械改写同步代码。
- `async def` 中禁止直接执行会长期阻塞 Event Loop 的同步网络或文件操作；应使用异步 SDK、线程边界或保留同步 Router，并明确取舍。
- Async Iterator 和 Generator 必须在 `finally` 中关闭外部 Stream、文件或连接。
- 客户端断开和任务取消不是普通 500；必须传播或转换为明确取消终态。
- Streaming 首次输出后不能假装仍可修改 HTTP 状态，也不能盲目重试造成重复输出。

## 7. Config、Secret 与常量

- 应用配置统一进入 Pydantic Settings，不在业务模块分散调用 `os.getenv()`。
- 密码、Token、API Key 和 Secret 使用 Secret 类型或受控配置，不写入代码、示例响应或日志。
- 具有部署差异的值进入配置；稳定业务规则可以使用命名常量。
- 增加配置时同步 `.env.example`、启动说明、校验和测试。

## 8. Logging 与错误

- 使用项目统一 Logger，禁止用 `print()` 记录应用事件。
- 日志记录结构化、固定字段和稳定原因，不直接拼接请求 Body 或外部异常全文。
- 成功日志只在业务最终状态已经明确后记录。
- 预期客户端错误不默认记为 ERROR；依赖不可用、补偿失败和数据不一致记录 ERROR。
- Service 抛领域异常，全局 Handler 负责 HTTP 映射；Service 不依赖 FastAPI `HTTPException`。

## 9. 注释与文档字符串

- 注释解释“为什么这样设计”、信任边界、并发语义或容易忘记的语言行为。
- 不逐行复述简单赋值和函数名已经表达的内容。
- 开发者为学习保留的准确中文注释不作为格式问题删除。
- 注释、TODO 和文档必须随行为更新；过期注释比没有注释更危险。

## 10. 测试与可测试性

- 新行为必须有与风险匹配的 Unit、API 或 Integration Test。
- 依赖通过构造参数或 FastAPI Dependency 注入，避免测试只能修改全局状态。
- Mock 在被测代码实际解析名字的位置替换。
- 外部 Provider 先用 Fake/Contract Test 验证稳定行为，再用真实 Integration Test 验证协议和故障。
- 测试不能因为真实依赖未启动而假通过；需要外部服务的测试使用明确 Marker 和启用条件。

## 11. 提交前检查

从 `backend/` 执行与变更范围相匹配的命令：

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
uv lock --check
```

数据库、Redis、MinIO 或外部 AI Provider 变更还必须运行对应 Integration Test。文档修改执行内部链接、标题层级、代码围栏和 `git diff --check` 检查。
