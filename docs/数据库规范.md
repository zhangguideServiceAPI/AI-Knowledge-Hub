# 数据库规范

## 1. 技术与职责边界

- 关系数据库使用 MySQL，ORM 使用 SQLAlchemy 2.x，结构变更使用 Alembic。
- Model 描述表、字段、关系和数据库约束。
- Repository 负责 SQLAlchemy 查询和写入，不包含 HTTP、对象存储或业务权限。
- Service 负责业务事务、跨 Repository 编排和补偿，不直接编写 SQL。
- Schema 不访问数据库，Router 不直接访问 Repository。

```text
Router -> Service -> Repository -> SQLAlchemy -> MySQL
```

## 2. Migration 是结构变更的唯一入口

禁止手工修改共享环境或生产数据库 Schema。所有表、字段、索引、约束和数据结构变更都必须通过 Alembic Migration 管理。

生成候选 Migration：

```bash
uv run alembic revision --autogenerate -m "describe schema change"
```

Autogenerate 只是草稿，必须人工 Review：

- Upgrade 和 Downgrade 是否对称。
- 表、字段、类型、默认值、可空性和外键是否符合设计。
- 索引和约束名称是否稳定。
- 删除或收窄字段是否可能破坏已有数据。
- MySQL 方言行为是否与 SQLite 或本地假实现不同。

## 3. Migration 验证流程

数据库结构变更至少验证：

```text
alembic upgrade head
  -> 检查真实 MySQL Schema
  -> alembic downgrade <previous_revision>
  -> alembic upgrade head
  -> alembic check
```

- Upgrade/Downgrade 必须在真实 MySQL 验证，不能只依赖 SQLite Test。
- Downgrade 如果可能丢失真实业务数据，必须在 ADR、Release 或 Migration 注释中明确运维边界。
- Migration 不在应用启动时隐式自动执行；部署流程单独控制结构升级。
- 已经进入共享历史的 Migration 原则上不改写，新增修复 Migration。

## 4. 命名、类型与时间

- 表、字段、索引和约束统一使用 `snake_case`。
- 主键、外键和对外 Resource ID 的类型必须在设计阶段确认，不随意混用。
- 金额和成本使用 Decimal 对应数据库精确数值类型，不使用 Float。
- 时间字段含义必须明确；API 时间使用 ISO 8601，数据库与 Python 时区策略保持一致。
- 业务状态使用受控 Enum/字符串和数据库约束，不能依赖任意自由文本。
- 大文件 Bytes 不写入 MySQL；数据库保存可查询、可授权的 Metadata。

## 5. 约束与索引

- 数据库约束是最终一致性防线，Schema 校验不能替代 Unique、Foreign Key、Check 等约束。
- 索引必须服务真实查询、排序或约束，不为每个字段机械加索引。
- 设计联合索引时按照过滤、排序和基数分析实际查询。
- 外键删除行为必须明确使用 Restrict、Cascade、Set Null 或业务软删除，不能依赖默认猜测。
- 业务可重复字段不要误设全局唯一，例如原始文件名或跨用户 SHA-256。

## 6. Transaction 边界

- Repository 默认执行 `flush()` 或查询，不自行 `commit()`。
- Service 使用一个明确事务组合多个数据库操作。
- 捕获数据库异常后先 `rollback()`，不能继续复用失败事务状态。
- 不在数据库事务中执行不受控的长时间外部网络调用，除非设计已明确锁和一致性代价。
- MySQL 与 Redis、对象存储或外部模型没有共享事务，必须使用状态、幂等、补偿或异步对账，不能假装数据库 Rollback 会撤销外部操作。

## 7. 数据生命周期与隐私

- 区分业务删除、软删除、状态不可见和物理清理。
- 需要补偿或审计的资源不能在外部操作完成前删除唯一定位信息。
- 密码只保存强 Hash；Refresh Token 只保存摘要；API Key、原始 Token 和 Secret 不写入业务表。
- AI Usage 默认不保存完整 Prompt、用户 Message 或模型回答正文；确需保存必须先设计用途、权限、保留期限和脱敏。
- 失败原因使用固定代码，不把堆栈、Provider 原始异常或敏感输入写入数据库。

## 8. Repository 测试

Repository Test 至少覆盖：

- 正常创建、读取、更新和排序分页。
- 不存在、其他用户和不可见状态。
- Unique、Foreign Key、Check 等数据库约束。
- `flush()` 后异常与 Service Rollback 行为。
- 新旧数据兼容和 Nullable 字段。

涉及 Redis、MinIO 或外部 Provider 的一致性必须在 Service 和真实 Integration Test 中验证，不能由 Repository Mock 代替。
