# ADR-0015 认证系统使用 Redis

## 状态

已接受（2026-07-27）

## 背景

认证系统需要保存登录失败计数、自动过期数据，以及后续的 Refresh Token Session、多设备登录索引和撤销状态。这些状态必须能够被多个 FastAPI 进程共享，并且需要明确的生命周期和并发语义。

FastAPI 进程内存只对单个进程可见，进程重启后数据丢失，也无法在多个实例之间共享。MySQL 适合保存用户等长期事实，但使用数据库定时清理短期计数、处理高频原子递增和实现秒级过期会增加额外复杂度。纯无状态 JWT 可以验证 Token 的签名和有效期，但不能单独提供服务端 Session 撤销、多设备状态和登录限流。

当前 Story 首先需要实现登录限流；后续 Session Architecture 还需要在相同基础设施上实现 Refresh Token 生命周期和多设备会话管理。

## 决策

- 使用 Redis 保存认证系统的临时共享状态，MySQL 继续作为用户长期数据的事实来源。
- 本地开发固定使用 `redis:7.4.2-alpine`，端口只绑定 `127.0.0.1`，使用带密码的 `default` 用户、AOF 和 Named Volume。
- 使用 Pydantic Settings 管理 Redis Host、Port、DB、Password、连接超时和操作超时。
- 所有业务代码共用集中创建的 redis-py 客户端；客户端自动重试次数为零，由具体业务决定操作是否适合重试。
- Readiness 检查 Redis，Redis 不可用时返回 HTTP 503；Liveness 不访问 Redis 等外部依赖。
- 登录失败计数使用 Redis String，最大失败次数和固定窗口时间由 Settings 配置，当前默认值为 60 秒内 5 次。
- 登录标识先去除首尾空格并转为小写，再使用 SHA-256 摘要构造 Redis Key，避免邮箱明文直接出现在 Key 中。
- 使用 Redis 事务一次提交 `INCR` 和 `EXPIRE NX`。`INCR` 原子增加失败次数，`EXPIRE NX` 只在 Key 尚无 TTL 时设置窗口，后续失败不会重置倒计时。
- 每次登录先用 `GET` 判断当前计数是否达到上限；未知邮箱或密码错误时记录失败，成功登录时用 `DEL` 清除失败计数。
- 第 5 次凭据错误仍返回 HTTP 401 并将计数写为 5；窗口内的后续请求在密码验证前返回 HTTP 429。
- Redis 操作失败时登录采用失败关闭策略，不绕过限流签发 Access Token，由 API 边界统一返回 HTTP 503，响应不暴露内部 Redis 实现。
- 后续 Session Architecture 可以使用 Hash 保存单个 Session 字段，并使用 Sorted Set 按最后活动时间维护用户的多设备 Session 索引；具体 Key 和生命周期由 ADR-0016 决定，本 ADR 不提前确定。

## 原因

- Redis 能在多个应用进程和实例之间共享认证状态。
- TTL 让登录计数和 Session 等临时数据按生命周期自动清理，不需要数据库清理任务。
- 原子命令和事务可以避免并发递增丢失，以及 `INCR` 成功但 TTL 未设置的失败窗口。
- 内存访问适合登录保护和 Session 校验等高频、低延迟操作。
- Redis 数据结构可以分别表达计数、对象字段和有序索引，而不需要把所有认证状态编码成单个字符串。
- 失败关闭可以避免攻击者在 Redis 故障期间绕过登录保护。

## 影响

- Redis 成为登录路径的必要依赖；Redis 不可用时应用进程仍然存活，但 Readiness 失败且登录返回 HTTP 503。
- AOF 和 Named Volume 提高本地重建后的数据恢复能力，但 Redis 仍不是用户长期事实的唯一存储。
- 运维需要管理 Redis 密码、容量、TTL、持久化和故障监控。自定义 ACL 用户和命令权限在生产安全加固时再设计。
- SHA-256 是确定性摘要，只能避免邮箱明文直接暴露，不能抵抗对常见邮箱的枚举猜测，也不等同于加密。未来安全加固可以改用独立 Secret 的 HMAC。
- 当前限流只按规范化邮箱维度计数。攻击者仍可跨大量账号进行密码喷洒，也可能故意让特定账号在 60 秒内无法继续登录；后续安全 Review 需要设计账号与可信客户端 IP 的双维度限流。
- `GET` 限流检查和凭据失败后的计数写入不是同一个原子步骤，并发请求可能在计数达到上限前同时通过检查。当前事务保证计数与 TTL 一起建立，但不提供严格的并发准入上限。
- 单元测试使用 Mock 验证 Redis 命令和业务分支，真实 Redis 用于验证 TTL、事务、密码认证、持久化和故障行为。
- 当前只完成 Redis Foundation 和登录限流，Refresh Token Session、Rotation、Logout 和多设备管理仍属于后续 Story。

## 未采用方案

- 只使用 FastAPI 进程内存：无法跨进程共享，重启后丢失，也不适合分布式部署。
- 使用 MySQL 保存所有短期计数和 Session 状态：可以实现，但 TTL 清理、高频递增和临时状态管理更复杂。
- 只使用无状态 JWT：无法满足服务端撤销、Refresh Token Rotation、多设备 Session 和登录状态管理。
- Redis 故障时绕过限流继续登录：可用性更高，但会在基础设施故障期间关闭安全控制，因此不采用。
- 对每次失败重新设置 TTL：会把固定窗口变成持续延长的窗口，可能让用户长时间无法恢复登录。
